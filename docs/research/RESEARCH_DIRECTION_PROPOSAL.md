# 研究方向讨论稿

**Research Direction Discussion Draft**  
项目：LLM Inference Benchmark & Bottleneck Analysis Platform  
日期：2026-10-12；用于与导师讨论，非论文、非正式论文计划书。本文没有认定创新已成立，不承诺发表。

## 1. 项目背景

LLM Serving 不仅需要提高吞吐，还需要控制首 Token 延迟、输出间隔和尾延迟。vLLM 的分页式 KV Cache、SGLang 的结构化程序执行与前缀缓存，为多请求、多轮调用提供重要系统基础；其机制及配置也改变评测结果。参考 [vLLM/PagedAttention](https://arxiv.org/abs/2309.06180)、[SGLang](https://arxiv.org/abs/2312.07104)。

固定请求长度、固定并发的测试适合可控对照，却不足以单独描述任务依赖、工具等待、时变到达、缓存共享和多租户竞争。本项目已完成的随机有限批次测试不代表真实生产容量。已有 [ServeGen](https://www.usenix.org/conference/nsdi26/presentation/xiang-servegen) 研究生产负载刻画；[XPerf](https://arxiv.org/abs/2608.20370) 研究 Agent 执行图和回放，因此不能把“增加动态负载或 Agent Benchmark”直接当作新研究贡献。

定位是保留可复现 Benchmark 工程底座，探索具体机制问题，再通过文献和实验判断是否值得形成论文。

## 2. 当前工程基础

### 系统架构与实现状态

已选定 FastAPI + SQLite + 单 GPU worker 的最小架构；**选定不等于已经全部实现**。当前可核查运行链路主要是 CLI 实验控制、官方请求客户端、采集及离线报告。

| 层次 | 当前代码与能力 | 后续计划 |
| --- | --- | --- |
| API 层 | 已有引擎 OpenAI-compatible completion 接入；项目自身 FastAPI 任务 API 尚未在主体仓库完成 | 提交任务、查询状态和结果；与引擎 API 区分 |
| Benchmark Controller | `study.py` 管理自有服务进程，`lab.py` 组织预热、重复、顺序与配置校验 | 接入任务生命周期、SQLite 索引、独立负载配置 |
| Worker | 已有串行单引擎实验执行方式，避免同 GPU 同时运行两个引擎；非已完成的持久任务 worker | 可恢复状态、失败记录及单 GPU 排他执行 |
| Metric Collector | 官方客户端 TTFT/TPOT/ITL、吞吐等原始结果；约 0.5 秒周期设备级 GPU 采集 | 在可观测时接入服务端缓存/调度事件，记录来源 |
| Analyzer | `lab.py` 对照报告、CSV/JSON/SVG/PNG；`tail_report.py` 请求级尾部证据分析 | 结果索引、浏览界面、统计检测与候选瓶颈证据 |

### 当前能力与限制

- 已有 vLLM/SGLang 同机同模型实验流程，记录模型 revision、引擎来源、软件版本、命令及硬件信息；预热和三次重复有明确流程。
- 2026-10-02 的历史固定并发研究包含 24 次运行、1,536 个请求；这是已有实验记录，不是本轮新增 Agent 测量。固定输入 1,024、输出 256 Token，缓存关闭，属于有限批次饱和负载。
- 核心 15 项 CPU 校验/报告测试此前已通过。本轮额外完成 9 项 GuideLLM 组件集成测试，使用真实 DAG/worker/回放代码和模拟后端、IPC、时钟，覆盖依赖等待、缺 duration、非法图及失败/取消。它们证明组件语义，不证明真实推理、HTTP 回放或缓存优化收益。
- 当前没有生产 trace、服务端请求事件链或经过验证的自动根因算法。客户端 queue_times 不等于引擎排队；设备利用率不能直接证明 memory-bound；缺失缓存命中指标必须标不可观测。
- 当前可用本机 RTX 4060 Laptop 8GB 与已有 Qwen2.5-0.5B 模型，适合功能初验；不能替代 A100/H100 或多卡论文复现。没有租用 GPU 或新增性能结论。

本人已有 vLLM 开源贡献经验及 SGLang 参与经验。贡献记录由既有资产审计和 GitHub 证据支撑；不能把“参与/待 review”写成“已合并”。这些经历有助于理解引擎接口、构造最小复现、设计回归测试及定位相关源码，但不自动证明独立算法创新。真实上游问题经最小复现、正确性测试及公平对照后才考虑 PR，公开提交另行确认。

## 3. 当前发现的问题

以下是待研究的问题描述，而非已经证实的新瓶颈或解决方案。

### Problem A：动态 Agent 工作负载是否会产生新的推理系统瓶颈？

传统单次调用可简化为 `request → generate → finish`；Agent 为 `task → reasoning → tool call → memory/context → continue generation`，并可能包含分支。长生命周期 session、工具期间的暂停状态、跨轮 cache reuse 及多任务竞争，可能改变缓存驻留和请求返回模式。

研究问题：**现有 KV Cache 管理和调度策略是否适用于 Agent 工作负载？**

需要收敛为可证伪问题：在相同模型和负载、充分调优的缓存保留与公平策略组合下，非平稳工具等待和集中返回是否仍使受保护租户的延迟/SLO 明显恶化？若现有组合已经充分解决，停止该创新声明。

已有 [Continuum](https://arxiv.org/abs/2511.02230) 处理多轮 Agent TTL，[FairInference](https://arxiv.org/abs/2609.18112) 处理 token 延迟隔离，[Justitia](https://arxiv.org/abs/2510.17015) 研究任务并行 Agent 公平性；不能宣称这些问题完全未被研究。Continuum 公开预览使用简单历史估计与固定阈值，不代表完整论文估计器；FairInference 正式源码本轮尚未确认。强基线可复现性仍是前置风险。

### Problem B：LLM Serving 性能下降是否可以自动定位原因？

TTFT、TPOT、P99 latency 的异常可能来自客户端等待、服务端 queue delay、prefill、decode、KV Cache 压力或 GPU 资源竞争。不同原因可能产生相似聚合指标；时间相关不能直接证明因果。

研究问题：**能否通过多源指标和 trace 信息实现自动瓶颈归因？**

初步边界是同模型、同硬件、版本/负载匹配的回归检测与候选原因排序，以已知干预/故障验证准确率和误报；和阈值、变点检测及专家规则对照。已有 [StriaTrace](https://www.usenix.org/conference/osdi26/presentation/wu-haonan) 研究追踪和诊断，普通仪表盘、告警规则与日志关联不算新增学术贡献。

### Problem C：动态负载下性能是否可以预测？

输入长度、并发/到达率、输出需求、缓存状态及硬件会共同影响 latency 和 throughput。需要明确预测对象、时间范围和误差要求，不能仅凭输入长度拟合均值就声称完整性能预测。

研究问题：**控制模型和硬件后，缓存状态与负载相位信息是否能减少既有预测方法在负载变化时的误差？**

已有 [Vidur](https://arxiv.org/abs/2405.05465) 采用 profiling 与仿真进行性能分析。训练与测试须按整条 trace/负载族分离，避免相邻请求泄漏；新硬件泛化必须另测。本方向尚未形成有证据支持的缺口。

## 4. 候选研究方向比较

资源等级为相对估计，不是已获资源或预算承诺。

| 方向 | 研究问题 | 优势 | 风险 | 资源需求 |
| --- | --- | --- | --- | --- |
| Agent Cache/Isolation | 暂停与集中返回下缓存复用和延迟隔离是否仍冲突 | 可结合现有 Benchmark、引擎贡献与 Agent Infra 场景 | 已有工作较多；强基线不完整；实际前缀与工具行为难控制 | 中：CPU 回放→本机小模型；更大模型可能需单卡 24–48GB，另行确认 |
| Bottleneck Diagnosis | 同条件回归能否检出并可靠缩小候选原因 | 复用最多；即使研究失败仍有工程价值 | 创新需收敛；指标不足、注入偏差；诊断正确性难判 | 低至中：CPU 检测与已知故障；必要的真实单卡服务验证 |
| Performance Prediction | 负载变化下延迟/吞吐预测是否更准确 | 容量评估价值明确 | 容易重复既有模型；校准成本和泛化风险 | 中：profiling 数据、隔离测试 trace、真实单卡校准 |

## 5. 推荐研究路线

保留 Benchmark 作为本科毕设工程底座；优先探索 **Agent 工作负载下的性能分析与优化问题**，目前不直接确定论文题目或算法。

理由是多轮任务/工具等待提供具体系统场景，现有实验配置与数据保存链路可复用，源码分析、回放正确性和性能验证也契合 AI Infra 求职。研究推进依靠“先证明现有强基线仍有问题，再考虑机制改进”，不是以趋势或工具功能数量证明创新。

若 2–4 周内无法复现强基线、获得有效 trace，或现有方法已解释并解决现象，则缩小/停止 Agent 创新探索，转向 **LLM Serving 性能退化检测与瓶颈定位**，重新审查文献和假设。备用方向同样不预设创新成立。性能预测先保留为观察方向，避免三条路线并行失控。

## 三轮自我审查与修订记录

1. **是否过泛？** 初稿的“Agent 瓶颈”无法直接测量；已缩为暂停/集中返回、受保护租户 SLO 和强策略组合。只设一个优先方向，另外两个作备用/观察。
2. **是否创新不足？** 多轮缓存、公平、追踪和预测均已有研究；已补最接近文献、公开代码与论文的差异、证伪及停止条件。没有声称已发现 research gap。
3. **工程与科研是否脱节？** 已将任务系统/可视化归工程验收，把方法差异、公平对照及实验验证归研究验收；共享基础设施，但科研失败不阻断毕设。架构选定与实现完成已明确区分。

适合导师沟通：能够快速看到已有证据、资源边界、三个问题和需要导师判断的事项。仍需导师确认主假设与基线范围后再推进算法；不能作为已经完成研究或投稿成熟度的证明。
